# rvm bootstrap redirect target. https://get.rvm.io is a permanent redirect to
# https://bitbucket.org/mpapis/rvm/raw/master/binscripts/rvm-installer, and
# rvm-reconcile.sh fetches it with `curl -fsSL` (-L follows the redirect), so
# allowlisting get.rvm.io alone is not enough — the bootstrap dies on the hop.
# rvm's own `rvm get stable` (reconcile's install-failure retry) re-fetches
# through the same redirect and reads its Location: header to build the
# signature URL, so this host is needed for the retry path too.
bitbucket.org
# The installer resolves the "stable" tag from api.github.com first and falls
# back to api.bitbucket.org. Anonymous api.github.com is rate-limited per public
# IP — shared by every container behind one NAT — and a 403 with the fallback
# blocked means "Exhausted all sources trying to fetch version", not a retry.
api.bitbucket.org

cache.ruby-lang.org

# The rvm signing keys are pre-seeded into /etc/skel/.gnupg at build, so a FRESH
# home verifies the installer without a keyserver. entrypoint.sh populates a home
# with `cp -rn` (no-clobber), so a group that already carries its own ~/.gnupg
# keyring keeps it and never receives them — the `host` group, mounting the real
# $HOME, is the case that matters. There the installer fetches the keys, and this
# is what lets it. Do not drop it because "the keys are baked in": they are baked
# into skel, not into every home.
keyserver.ubuntu.com

# rvm's PREBUILT-BINARY mirrors. There are THREE, and rvm HEAD-probes ALL of
# them on every `rvm install`, whichever Ruby you asked for. Verbatim from its
# config/db — keep this list in sync by grepping the FIELD NAME, never the
# hostnames:
#
#   rvm_remote_server_url =https://rvm-io.global.ssl.fastly.net/binaries
#   rvm_remote_server_url1=https://repo1.maven.org
#   rvm_remote_server_path1=maven2/org/jruby/jruby-dist
#   rvm_remote_server_url2=https://rubies.travis-ci.org
#
# url1 is Maven Central because that is where JRuby is published, and rvm probes
# it even for CRuby: installing 3.4.5 issues a HEAD for
# repo1.maven.org/maven2/org/jruby/jruby-dist/ruby-3.4.5.tar.bz2, which cannot
# exist. Blocking any of them is not fatal — rvm falls back to compiling from
# source, which is why Ruby installs worked anyway — but each costs a --max-time
# 5 stall per address and leaves a permanent entry in blocked-domains.txt that
# reads like a misconfiguration.
#
# HOW url1 WAS MISSED, because the next person will make the same mistake: the
# first pass through config/db grepped for `fastly|travis|binary`. That matched
# the two mirrors whose hostnames contain those words and silently skipped the
# one that does not — the grep pattern chose the answer. Finding it again took
# two full verification rounds and a live /proc/net/tcp probe to catch the curl
# in flight. Grep `rvm_remote_server` and read every hit.
#
# BOTH spellings of the Fastly host are listed on purpose. Fastly's legacy
# <service>.global.ssl.fastly.net form treats "-" and "_" interchangeably, and
# the two resolve to an identical A-record set; rvm's config/db requests the
# HYPHEN form while the blocked-capture DNS map recorded the UNDERSCORE one. The
# ipset would be correct with either (same IPs), but self-healing matches by
# NAME, so listing only one leaves the other reported as blocked forever.
rvm-io.global.ssl.fastly.net
rvm_io.global.ssl.fastly.net
rubies.travis-ci.org
# Also listed in openjdk.txt, for the unrelated JDK/Maven-build case. It must be
# in BOTH: openjdk.txt is only assembled when a JVM key is set, so a Ruby-only
# image would never get it from there — which is exactly the configuration this
# was found in.
#
# An image with both Ruby and a JDK therefore gets the line twice. build.sh does
# NOT de-duplicate (include_fragment just cats each file; the only `sort -u` is
# over tool fragment NAMES), and that is harmless here: the refresher does
# `ipset add … -exist` and the self-healer uses `grep -qxF`, so a repeat costs
# one redundant getent per cycle and nothing else.
repo1.maven.org
