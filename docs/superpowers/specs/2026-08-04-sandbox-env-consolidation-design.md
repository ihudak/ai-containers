# `sandbox.env` Launcher-Config Consolidation

_Design spec — 2026-08-04_

## Goal

Move the launcher configuration out of the generated `runme.sh` into env files, split
into a **portable** layer (`sandbox.env`, tracked) and a **machine-specific** layer
(`sandbox.local.env`, gitignored). `runme.sh` becomes a thin wrapper. A single loader in
`sandbox-common.sh` gives every entry point the same config, with precedence **inline env
> `sandbox.local.env` > `sandbox.env`**.

## Background & Motivation

Today `project-init.sh` generates a per-project `runme.sh` that bakes the launcher config
inline as `export`s (`project-init.sh:318-364`):

```bash
export IMAGE_NAME=…
export CONTAINER_CPUS=…  CONTAINER_MEMORY=…  CONTAINER_MEMORY_RESERVATION=…  CONTAINER_MEMORY_SWAP=…
export AI_CONTAINER_GROUP=…
[export AI_CONTAINER_GROUP_INIT=…]     # conditional
[export EXTRA_MOUNTS="…"]              # conditional, machine-absolute paths
…
./build.sh
./sandbox.sh open ..                   # mode + workdir hardcoded
```

Separately, `project-init.sh:277-284` writes a `sandbox.env` holding **only** `IMAGE_NAME`,
which `sandbox-common.sh:46-49` sources (when `IMAGE_NAME` is unset) so direct
`build.sh`/`sandbox.sh`/`repo.sh` runs resolve the same image. Problems:

- **`IMAGE_NAME` is duplicated** across `sandbox.env` and `runme.sh`.
- **Config lives inside a generated file.** Re-running `project-init.sh` (or a future
  `sync-to-projects.sh` that wanted to update the launcher's *logic*) risks clobbering
  hand-edited config, because data and wrapper are the same file.
- **The whole mount strategy is machine/platform-specific, not just `EXTRA_MOUNTS`.**
  `.ai-containers/` is blanket-gitignored in the consumer repo *because* the launcher
  embeds machine-absolute paths (`project-init.sh:69-71`). But bind-vs-named-volume is a
  macOS-vs-Linux decision: big repos on macOS **must** use named volumes (`REPOS`), which
  are pointless on Linux; the working directory (the positional arg to `sandbox.sh`) is a
  bind `..` on Linux but often a named volume `@name` on macOS. Moving a project
  Linux→macOS means rewriting exactly `EXTRA_MOUNTS`/`REPOS`/workdir while everything else
  stays. There is no seam that quarantines "how *this machine* mounts things," so no part
  of the config can be shared across a team.

## Non-Goals

- **`container.env` is untouched.** It is a distinct layer — the *in-container app env*,
  auto-detected by `sandbox.sh` (`:733-736`) and passed **into** the running container.
  This spec concerns *host-side launcher* config only.
- **Not force-flipping `.ai-containers/` to tracked.** This spec delivers the split
  *mechanism* (portable vs local) and gitignores `sandbox.local.env`; whether a team then
  commits `.ai-containers/` (by removing the blanket ignore) stays a per-project opt-in.
- **No new pinning or schema versioning** for the env files (they are not `sandbox.conf`).

## Architecture

### 1. Files

- **`sandbox.env`** (tracked, portable defaults). Holds project-level config that is the
  same on any machine: `IMAGE_NAME`, `AI_CONTAINER_GROUP` (+ `AI_CONTAINER_GROUP_INIT`),
  `CONTAINER_CPUS`, `CONTAINER_MEMORY` (+ reservation/swap), `SANDBOX_MODE` (default
  `open`), `SANDBOX_WORKDIR` (default `..`). Includes **commented** `EXTRA_MOUNTS`/`REPOS`
  examples for discoverability. `KEY=value` lines (sourced context; no `export` needed —
  the loader exports).
- **`sandbox.local.env`** (gitignored, this machine). Absent by default. Holds the
  machine/platform-specific mount strategy — `EXTRA_MOUNTS`, `REPOS` — and **any override**
  of a portable key (e.g. a different `AI_CONTAINER_GROUP` — group names can legitimately
  differ per machine — `SANDBOX_WORKDIR=@app`, a larger `CONTAINER_MEMORY`, a different
  `SANDBOX_MODE`). Because it is loaded at higher precedence than `sandbox.env`, nothing in
  `sandbox.env` is locked.
- **`runme.sh`** (thin, generated). No config baked in:
  ```bash
  #!/usr/bin/env bash
  # runme.sh — launch the AI sandbox for <project>. Generated by project-init.sh.
  # Config lives in sandbox.env (portable) and sandbox.local.env (this machine).
  set -euo pipefail
  cd "$(dirname "${BASH_SOURCE[0]}")"
  # Build-time GitHub token for private tool downloads (non-clobbering, gh-optional):
  if command -v gh >/dev/null 2>&1; then : "${GITHUB_TOKEN:=$(gh auth token 2>/dev/null || true)}"; export GITHUB_TOKEN; fi
  ./build.sh
  ./sandbox.sh          # mode + workdir come from SANDBOX_MODE / SANDBOX_WORKDIR
  ```
  The `REPOS`/network-mode comment hints move into `sandbox.env` as commented examples.

### 2. Single loader in `sandbox-common.sh`

Replace the current IMAGE_NAME-only `source` block (`:41-49`) with a loader that reads a
file line-by-line and sets each `KEY` **only if it is currently unset** (set-if-unset), so
the first source to define a key wins:

```bash
# Load KEY=value lines from an env file as defaults: sets a key ONLY if it is not
# already set, so an inline/exported env var always wins. Ignores blank/comment lines,
# tolerates a leading `export`, strips surrounding double quotes. Parsing (not sourcing)
# keeps it to KEY=value assignments — no arbitrary code runs.
load_env_defaults() {
  local file="$1" line key val
  [[ -f "$file" ]] || return 0
  while IFS= read -r line || [[ -n "$line" ]]; do
    line="${line#"${line%%[![:space:]]*}"}"          # ltrim
    [[ -z "$line" || "$line" == \#* ]] && continue
    line="${line#export }"
    [[ "$line" == *=* ]] || continue
    key="${line%%=*}"; val="${line#*=}"
    [[ "$key" =~ ^[A-Za-z_][A-Za-z0-9_]*$ ]] || continue
    val="${val%\"}"; val="${val#\"}"                  # strip one layer of surrounding quotes
    [[ -n "${!key:-}" ]] && continue                  # already set (inline/earlier file) wins
    printf -v "$key" '%s' "$val"; export "$key"
  done < "$file"
}

# Precedence: inline env > sandbox.local.env > sandbox.env. With set-if-unset, the source
# loaded FIRST wins, so local is loaded before portable.
load_env_defaults "${script_dir}/sandbox.local.env"
load_env_defaults "${script_dir}/sandbox.env"
```

Because every host entry point sources `sandbox-common.sh` (`build.sh`, `sandbox.sh`,
`repo.sh`), all of them now get the full config — a direct `./sandbox.sh` run honors
`CONTAINER_CPUS`/`MEMORY`/`EXTRA_MOUNTS`/`REPOS`, not just `IMAGE_NAME`. A one-off inline
override (`CONTAINER_MEMORY=8g ./sandbox.sh`) still wins because the key is already set
before the loader runs.

### 3. `sandbox.sh` mode/workdir from env

`sandbox.sh` takes `<mode> <workdir>` positionally (`./sandbox.sh open ..`,
`./sandbox.sh discovery @app`). Add env defaults so the positional args become optional:
when arg 1 is absent, mode defaults to `${SANDBOX_MODE:-open}`; when arg 2 is absent,
workdir defaults to `${SANDBOX_WORKDIR:-..}`. **Fully backward-compatible** — an explicit
positional arg still wins, so every existing invocation is unchanged. This is what lets
`runme.sh` call a bare `./sandbox.sh`. `SANDBOX_MODE`/`SANDBOX_WORKDIR` are populated by
the loader (§2) from the env files.

### 4. `project-init.sh`

- **Write `sandbox.env`** with the prompted portable values (`IMAGE_NAME`,
  `AI_CONTAINER_GROUP`(+init), the `CONTAINER_*` values, `SANDBOX_MODE=open`,
  `SANDBOX_WORKDIR=..`) plus commented `EXTRA_MOUNTS`/`REPOS` examples.
- **Write `sandbox.local.env`** only when the user supplied machine paths at init: the
  resolved `EXTRA_MOUNTS` (absolute paths) go here, **not** into `runme.sh`. If no machine
  paths were given, `sandbox.local.env` is not created (its absence is a clean no-op).
- **Write the thin `runme.sh`** (§1). The existing overwrite prompt for an existing
  `runme.sh` stays.
- **Gitignore `sandbox.local.env`** in `.ai-containers/.gitignore` (add to the pattern
  list at `:298-304`). `sandbox.env` stays *not* ignored (it is portable/trackable).
- `sync-to-projects.sh` continues to **not** overwrite `sandbox.env` or `sandbox.local.env`
  (per-project config), and does not generate `runme.sh` (that is `project-init.sh`'s job).

### 5. Precedence (worked)

For any key, the value comes from the highest-precedence source that defines it:

| defined in | winner |
|---|---|
| inline env (`KEY=v ./sandbox.sh`) + local + portable | inline |
| local + portable | local |
| portable only | portable |
| nowhere | unset (falls back to code defaults, e.g. `SANDBOX_MODE:-open`) |

## Error Handling & Edge Cases

- **Missing `sandbox.local.env`** — `load_env_defaults` returns 0 on a missing file; a
  no-op. The common (single-machine, no extra mounts) case has no local file.
- **Malformed lines** — non-`KEY=value` lines and invalid identifiers are skipped; only
  simple assignments are honored. Parsing (not sourcing) means a stray command in the file
  cannot execute.
- **Quotes** — one layer of surrounding double quotes is stripped (so
  `EXTRA_MOUNTS="/a /b"` yields the intended value). Values with embedded spaces must be
  quoted, matching the current `runme.sh` `export EXTRA_MOUNTS="…"` convention.
- **Empty `SANDBOX_MODE`/`SANDBOX_WORKDIR`** — `sandbox.sh` applies `:-open` / `:-..`
  fallbacks, so an env file that omits them still launches.
- **Direct-run behavior change (intended):** `./sandbox.sh` run outside `runme.sh` now
  applies `CONTAINER_*`/`EXTRA_MOUNTS`/`REPOS` from the files, where before it applied only
  `IMAGE_NAME`. This is the desired consistency; documented in the migration note.

## Migration

- **Existing projects keep working** — their current fat `runme.sh` still runs (it just
  `export`s inline, which the new loader treats as already-set and leaves alone).
- **To adopt the new shape**, re-run `project-init.sh` (it regenerates `sandbox.env` +
  thin `runme.sh`, and writes `sandbox.local.env` for machine paths), **or** manually:
  move the portable `export`s from `runme.sh` into `sandbox.env` (as `KEY=value`), move
  `EXTRA_MOUNTS`/`REPOS` into `sandbox.local.env`, and replace the launch line with
  `./sandbox.sh`. A short "Migrating an existing runme.sh" subsection goes in the README.
- **fip** adopts it as part of the pending re-sync (BACKLOG §5): `sync-to-projects.sh`
  refreshes the shared scripts, then a `project-init.sh` re-run produces the new launcher
  shape.

## Testing

- **`tests/test-env-file.sh`** (exists) — extend to cover `load_env_defaults`:
  - precedence: inline > local > portable (set a key in all three, assert inline wins;
    then local-only, assert local; then portable-only, assert portable);
  - a missing `sandbox.local.env` is a clean no-op;
  - comment/blank lines and a leading `export` are handled; surrounding quotes stripped;
    a non-assignment line is ignored (and does not execute);
  - an already-exported var is not clobbered.
- **`sandbox.sh` mode/workdir defaulting** — a focused test (stub/argument-level): no
  positional args → uses `SANDBOX_MODE`/`SANDBOX_WORKDIR`; an explicit positional arg wins;
  empty env → `open`/`..` fallback.
- **`tests/test-sync-project.sh`** — if the shared-file set or the `.ai-containers/.gitignore`
  pinned patterns change (adding `sandbox.local.env`), update the pinned contract in
  lockstep.
- Full suite stays green; no schema migration involved.

## Risks & Mitigations

- **Precedence surprise** — the set-if-unset/local-first mechanism is non-obvious.
  Mitigation: the loader carries the precedence comment, the README documents "highest
  source that defines the key wins," and the test pins all three precedence cases.
- **Direct-run behavior change** — advanced users running `./sandbox.sh` directly now get
  resource limits/mounts they did not before. Mitigation: this is the intended
  consistency; called out in the migration note. Any prior reliance on "direct run =
  unlimited" is served by an empty/omitted key or an inline override.
- **A committed `sandbox.env` leaking a machine path** — only if a user hand-edits a
  machine path into the portable file. Mitigation: `EXTRA_MOUNTS`/`REPOS` are only
  *commented examples* in `sandbox.env`; `project-init.sh` writes real machine paths to
  `sandbox.local.env`; the README states the rule.
